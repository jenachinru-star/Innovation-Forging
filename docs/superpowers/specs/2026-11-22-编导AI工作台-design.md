## 1. 背景与赛题要求

### 1.1 赛题原文摘要

- 创作主题：帮编剧、导演完成一件具体工作。
- 要求：围绕剧本创作或排演筹备，选择一项明确任务，制作能够处理实际材料、输出工作成果的工具。
- 官方示例方向（仅供参考，非必须采用）：
  1. 《一键拆剧本》：上传剧本，按场次整理人物、地点和道具，生成可编辑的排演准备表。
  2. 《人物关系整理器》：根据剧本梳理人物关系，标注冲突及对应情节。
  3. 《剧本版本对照助手》：对比两版剧本，标出增删台词、场次变化及涉及角色。

### 1.2 整体要求（硬约束）

1. 强制使用 Node.js 为技术栈。
2. 在"我的现场"中根据提示连接 agent。
3. 用 agent 检测 dist 合规性。
4. 用 agent 将作品打包成压缩包，并获取文件地址。
5. 在平台前端上传压缩包。
6. 核心功能：至少实现一条可完整体验的核心流程，支持用户输入或操作，并产生相应的剧情变化或处理结果，**不得仅提交静态页面或功能概念展示**。
7. 交付建议：建议提供 1 份作品封面，尺寸 16:9；如不提交，则为平台默认封面。

说明：第 2-5 条是比赛平台的**提交流程**（由 arena-skill 协助完成），不属于产品功能开发范畴，本文档不展开设计，仅在"交付物"章节提及。

### 1.3 团队现状与约束

- 团队为团队参赛，全员以 AI 辅助编程（vibe coding）为主，无资深工程师。
- 实际可用开发时间约 4 天（2026-11-22 至 2026-11-26）。
- 需要控制技术方案的复杂度和出错面，优先选择文档资料丰富、AI 辅助编码准确率高的主流技术栈。

## 2. 产品定位

**一句话定位**：从零散创作素材到可排演剧本的 AI 全流程工作台——帮编导把"脑子里的想法/对话片段"一路带到"可以开始排练"的状态。

**完整故事线**（用于产品叙事和 Demo 讲解）：

1. 用户有一些零散的创作素材（对话片段、情节想法、人物设定文字），这是创作初期最真实的状态。
2. AI 帮忙把这些素材整理生成一份规范格式的剧本（分幕分场、人物台词、舞台提示）。
3. 用户确认/编辑剧本后，AI 自动解析出结构化数据。
4. 工作台基于这份结构化数据，展示排演准备表、人物关系图，帮助导演/编剧进行排演筹备。

**产品定位决策依据**：

- 赛题要求"选择一项明确任务"，但赛题原文"围绕剧本创作**或**排演筹备"本身包含编剧（创作）和导演（排演筹备）两个阶段。将两者串联为"一条完整故事线"（素材→剧本→排演筹备），而非"两个拼接的独立工具"，既覆盖了编导工作的真实全貌，又保持了叙事上的单一性和聚焦感，不会显得功能堆砌。
- 排演准备表与人物关系图共享同一份"剧本结构化数据"，核心 AI 解析逻辑只需实现一次，显著降低开发量和出错环节，适配团队无资深工程师、时间紧张的现状。

## 3. 完整功能链路

```
【素材输入】自由文本框，用户输入想法/对话/人设（任意混合，不要求用户区分输入类型）
    ↓
AI 生成剧本文本
    - 若素材信息不足以展开成剧本：AI 直接在回复中反问细节（渐进式澄清），不报错、不强行编造
    - 若 API 调用本身失败：自动重试 2 次，仍失败则提示用户"生成失败，请重试"并提供"重新生成"按钮
    ↓
用户查看/编辑生成的剧本文本
    - 可直接编辑文本内容
    - 可点击"重新生成"重新调用上一步（不影响已输入的素材）
    ↓（用户确认满意，点击"确认，下一步"）
AI 解析剧本文本成结构化数据（ScriptData，见第 5 节）
    - 容错解析：先尝试直接 JSON.parse，失败则剥离多余文本后重试一次
    - 仍失败：自动重新请求 AI 一次，并在 prompt 中强化"只输出纯 JSON"的约束
    - 仍失败：提示用户"解析失败，请重试"并提供"重新解析"按钮
    - 对人物关系等主观判断内容，AI 输出时需附带 needsReview 置信度标记
    ↓
┌──────────────────────────┬──────────────────────────────┐
│   排演准备表 Tab            │   人物关系图 Tab                │
│  （出场人物/场景/道具/        │  （ECharts 关系图；降级方案：      │
│   预估时长/剧情摘要，均来自   │   卡片列表）                     │
│   AI 解析结果，逐场展示）      │  - 若关系数组长度为 0，显示      │
│                            │    "暂无足够的人物关系信息"       │
│                            │  - needsReview=true 的关系      │
│                            │    高亮展示，提示用户重点核实      │
└──────────────────────────┴──────────────────────────────┘
```

### 3.1 关键设计原则

- **AI 生成的所有结果都是"可编辑的草稿"，不是不可更改的最终结果**。因为 LLM 的文本生成与理解本质是概率性的，无法保证 100% 准确，必须给用户留出纠错空间。
- **"失败处理机制"解决的是技术性失败（崩溃、格式错误），不是内容准确性问题**。内容层面的理解偏差，交由置信度标记 + 用户编辑能力兜底，不存在能自动判定"内容对不对"的机制。
- **渐进式澄清**：输入信息不足时，模拟真人编剧顾问的工作方式——不直接拒绝，也不凭空编造，而是通过 AI 自身的回复反问必要细节，让用户在同一个输入框补充后重新生成。

## 4. 功能范围与优先级

### 4.1 核心功能（必做，MVP 边界）

| 序号 | 功能 | 说明 |
|---|---|---|
| 1 | 素材输入 → AI 生成剧本文本 | 含渐进式澄清、重试机制 |
| 2 | 剧本文本确认/编辑 | 纯前端编辑，不调用 AI |
| 3 | AI 解析剧本 → 结构化数据 | 含容错解析、重试机制、置信度标记 |
| 4 | 排演准备表 Tab | 表格形式展示场次数据 |
| 5 | 人物关系图 Tab | ECharts 关系图，含降级方案 |

### 4.2 加分项（时间允许时按此优先级依次实现）

| 优先级 | 功能 | 说明 |
|---|---|---|
| 1 | 排演表/关系图手动编辑 | 用户可直接修正 AI 识别有误的内容 |
| 2 | 角色形象插画生成 | 风格化插画（非写实人脸），主要人物优先，固定风格描述词模板 |
| 3 | 角色海报墙 | 复用角色插画数据的另一种展示视图 |
| 4 | 剧本版本对照功能 | 官方示例方向之一，对比两版剧本差异 |
| 5 | 走位示意动画 | 纯前端动画实现（非 AI 生视频），模拟人物在简化舞台图上的位置变化 |

### 4.3 明确不做的事项（及理由）

| 事项 | 不做的理由 |
|---|---|
| 接入 AI 生视频服务 | 生成耗时长、质量不可控、demo 现场翻车风险高；真正有价值的"动态展示需求"（走位示意）更适合用前端动画实现，不需要 AI 视频生成能力 |
| 写实风格人物肖像 | 容易触发 AI 生图平台的内容审核限制；且与戏剧海报的艺术气质不符，改用风格化插画 |
| 浏览器本地历史记录（刷新保留进度） | Demo 现场会主动控制演示节奏，意外刷新概率低；相应的额外开发成本（本地存取逻辑）在当前时间约束下不划算 |
| 数据库持久化存储 | 产品流程是单次会话式（输入→处理→查看结果），不需要长期存储用户历史；省去数据库选型/建表/连接的复杂度和出错面 |

## 5. 数据结构定义

### 5.1 ScriptData（AI 解析剧本后的结构化数据，前后端通信的核心契约）

```
ScriptData {
  scenes: [                     // 场次列表
    {
      sceneNumber: number,        // 第几场
      title: string,              // 场次标题，如"第一场"
      location: string,           // 场景/地点
      characters: string[],       // 本场出场人物名字列表
      props: string[],            // 本场道具清单
      summary: string,            // 剧情摘要
      estimatedMinutes: number    // AI 估算的预估时长（分钟）
    }
  ],
  summary: string,               // 整部剧本的一句话总体简介
  characters: [                  // 全剧人物总表
    {
      name: string,                // 人物名字
      description: string          // 人物简介（用于生成形象图的描述来源）
    }
  ],
  relationships: [                // 人物关系列表
    {
      from: string,                 // 人物 A 名字
      to: string,                   // 人物 B 名字
      relation: string,             // 关系描述
      needsReview: boolean          // true = AI 判断把握不足，建议用户核实
    }
  ]
}
```

该结构既是 AI 解析接口的输出格式约束（prompt 中会要求 AI 严格按此结构输出 JSON），也是前端渲染排演表/关系图的数据来源。前后端基于这份契约可以并行独立开发。

## 6. 技术架构

### 6.1 整体架构

单体 Node.js 应用，前后端合并部署，不拆分为独立服务，不引入数据库。

```
┌───────────────────────────────────────────┐
│                Node.js 应用                  │
│  ┌──────────────┐      ┌─────────────────┐  │
│  │  前端 (React/  │ HTTP │   后端 API 路由    │  │
│  │   Vite)       │ <──> │  (Express)       │  │
│  └──────────────┘      └────────┬────────┘  │
│                                  │           │
│                          ┌───────▼───────┐   │
│                          │ 调用外部 LLM/    │   │
│                          │ 生图 API        │   │
│                          └───────────────┘   │
└───────────────────────────────────────────┘
       后端无状态，不持久化数据，数据随请求返回给前端自行持有
```

**架构决策依据**：

- 团队无资深工程师、时间紧张，架构复杂度必须降到最低。省去数据库、省去前后端分离部署的跨域配置，能显著降低踩坑概率。
- 后端无状态设计天然规避"多人并发使用时数据互相覆盖"的问题——每个请求独立处理，处理结果直接返回给发起请求的前端，不在服务端留存，不同用户之间不会互相影响。

### 6.2 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 后端框架 | Express.js | 最主流、文档资料最多，AI 辅助编码的训练数据覆盖最充分，出错率最低 |
| 前端框架 | React + Vite | 组件化管理多 Tab、可编辑文本、关系图等较复杂的 UI 状态；Vite 构建产出标准 dist，满足比赛打包要求 |
| 关系图可视化 | ECharts（Graph 关系图组件） | 声明式配置、文档示例丰富，AI 辅助生成代码准确率高；降级方案为纯 HTML/CSS 卡片列表，技术风险最低 |
| 文本生成/解析 AI | DeepSeek API（OpenAI 兼容接口） | 中文创作类任务表现稳定，调用方式业界资料丰富，接口格式与主流生态兼容 |
| 图片生成 AI（加分项） | Seedream（火山方舟 Ark 平台） | 用户已提供账号信息；风格化插画方向，不追求写实人脸；是否支持图生图/风格参考能力需在开发阶段实际验证 |
| 数据存储 | 无数据库，内存/请求级别处理 | 单次会话式流程不需要持久化，详见 4.3 |
| 页面状态管理 | React 原生 useState（单页面 + 阶段状态切换），不引入路由库/Redux | 页面流程是线性的，不需要处理浏览器前进后退；降低团队学习成本和出错面 |

### 6.3 后端接口定义

```
POST /api/script/generate
  输入: { material: string }                    // 用户输入的素材文本
  输出: { scriptText: string }                   // AI 生成的剧本文本（Markdown 格式）
  失败: { error: string, needMoreInfo?: boolean } // needMoreInfo 为 true 时，error 内容是 AI 的追问

  内部 prompt 设计要求：采用"先列分场大纲、再逐场展开台词"的两段式结构（即一次 API
  调用内，要求模型先输出简要的分场大纲（每场的核心人物与事件），再基于大纲展开完整
  台词），而非一次性直接生成完整剧本文本。目的是降低长剧本中人物名字、情节前后不
  一致的概率，不增加额外的 API 调用次数。

POST /api/script/parse
  输入: { scriptText: string }                   // 用户确认的剧本文本
  输出: { scriptData: ScriptData }                // 见第 5.1 节
  失败: { error: string }

POST /api/character/generate-image   （加分项）
  输入: { name: string, description: string }
  输出: { imageUrl: string }
  失败: { error: string }

POST /api/cover/generate   （作品封面图，独立交付物，非产品运行时功能）
  输入: { title: string }
  输出: { imageUrl: string }
```

### 6.4 AI 调用编排逻辑

- 点击"重新生成"（剧本确认页）：仅重新调用 `/api/script/generate`，不触发解析。
- 点击"确认，下一步"：调用 `/api/script/parse`。
- 若在工作台结果页发现解析结果不满意：提供"返回编辑剧本"按钮回到剧本确认页，编辑后重新调用 `/api/script/parse`；**不需要**重新调用 `/api/script/generate`（剧本文本已存在，无需重新生成）。

设计原则：每一步只重新执行"必要的那一步"，避免无谓的重复 AI 调用，兼顾响应速度、调用成本与用户操作直觉。

### 6.5 安全要求

- **DeepSeek API Key、Seedream API Key 必须只存在于后端环境变量中，绝不出现在前端代码或打包后的 dist 产物中**。前端只调用本应用自己的后端接口，由后端代理转调外部 AI 服务。这是基本的安全红线，前端代码会被打包进 dist 并可被任何访问者查看源码。
- 仓库中不提交任何包含真实密钥的文件；提供 `server/.env.example` 作为环境变量名称示例（不含真实值），真实密钥由各开发者在本地创建 `server/.env` 自行填入，该文件已列入 `.gitignore`。

### 6.6 输出格式稳健性优化

- `/api/script/parse` 调用 DeepSeek API 时，需先确认该接口是否支持"JSON 模式/结构化输出"参数（不同服务商的叫法可能是 `response_format: json_object` 或类似机制）。若支持，应优先启用该参数，让模型在服务端层面被强制输出合法 JSON，而不是仅依赖 prompt 中"请输出 JSON"的软约束。这能从源头减少"输出格式错误"类失败的发生概率，是对第 3 节已有的"容错解析 + 重试"机制的进一步加固，两者不互斥、应同时采用。

## 7. 边界情况处理

| 情况 | 处理方式 | 决策依据 |
|---|---|---|
| 用户输入素材信息严重不足/无法理解 | AI 在生成回复中直接反问必要细节（渐进式澄清），不报错、不强行编造无关内容 | 模拟真人编剧顾问工作方式，比机械的"请输入更多信息"提示更自然，且不需要额外的规则引擎判断"输入是否够长" |
| 人物/场次数量很少 | 不采用人数阈值判断，改为依据"关系数组长度是否为 0"判断是否展示关系图提示语 | 人数阈值是不准确的代理指标（人少但关系复杂、人多但关系稀疏的情况都存在），"是否存在可展示的关系数据"是更直接、更简单的判断依据 |
| AI 生成/解析的内容存在错误 | 不存在自动纠错机制，通过置信度标记（needsReview）提示用户重点核实，并将"可编辑"作为必做的兜底能力（剧本文本）和加分项（表格/关系图） | LLM 的语义理解偏差无法通过程序自动检测，只能通过人工介入纠正；这是所有 AI 应用类产品的现实边界，不应过度承诺"自动保证正确" |
| 用户刷新页面导致进度丢失 | 不做本地缓存兜底，接受此限制 | Demo 现场可控节奏，意外刷新概率低；对应的开发成本在当前时间约束下优先级不高 |
| 同一人物在剧本文本中前后名称不一致（如前文"老王"、后文"王大爷"实为同一人） | 不在后端做自动归一化判断（无法保证准确），依赖剧本确认页的"可编辑"能力，由用户在生成剧本阶段发现并手动统一名称；解析阶段如仍有残留不一致，体现为 characters/relationships 中出现看似重复的人物，用户可在加分项"手动编辑"功能中合并修正 | 名称归一化本质也是语义判断问题，和内容准确性问题同属 LLM 的现实边界（见上一条"AI 生成/解析的内容存在错误"），不额外引入规则引擎去"猜测"两个名称是否指同一人，避免引入新的误判来源 |

## 8. 风格统一设计（角色插画 + 封面图，加分项）

### 8.1 整体视觉风格方向

考虑到主题是"戏剧"，视觉风格采用"戏剧氛围 + 清晰工具感"的折中方案：

- 首页/封面区域：深色背景，酒红/金色点缀，衬线字体点缀标题，营造剧场节目单/舞台灯光的氛围感。
- 工作台功能区域（排演表、关系图）：以内容清晰可读为优先，保持与整体一致的配色基调，但减少装饰性元素，避免氛围设计影响信息阅读效率。

### 8.2 角色插画与封面图的风格统一机制

"风格统一"拆解为四个可控维度：绘画技法/媒介感、色彩基调、细节繁简程度、构图/取景方式。实现方式是构建一套**固定的风格描述词模板**，在每次调用生图 API 时自动拼接到提示词中，仅人物的具体特征描述（年龄、性别、气质等）部分随人物不同而变化，风格描述词部分完全固定不变。作品封面图若采用 AI 生图能力制作，同样套用这套风格描述词模板，确保与角色插画视觉统一。

**重要限制说明**：固定风格描述词能够显著提高生成结果"属于同一视觉体系"的概率,但不能保证像素级/笔触级的完全一致，这是当前 AI 生图技术的现实水平，设计上不应过度承诺绝对统一。

### 8.3 Seedream 图生图能力的渐进式采用策略

团队使用的生图服务为 Seedream（经火山方舟 Ark 平台调用）。该系列模型通常具备图生图（以参考图生成新图）的能力，但具体到当前使用的模型端点是否支持、效果如何，需在开发阶段实际发起测试请求验证，设计阶段不预先假定。采用策略分两步：

1. **基础方案（确定可行）**：使用 8.2 节所述的固定文字描述词模板，这是不依赖图生图能力、必定可执行的方案。
2. **增强方案（择机采用）**：若开发中验证确认该模型端点支持图生图/风格参考，则调整为"先生成第一个主要人物的插画作为风格锚点，后续人物生成时将该图作为参考图一并传入"，以进一步提升风格统一的稳定性。该方案是对基础方案的增强，不替代基础方案，若验证不支持或效果不佳，直接回退使用基础方案即可，不影响整体功能可用性。

## 9. 交付物
